# Dr. Ai backend request lifetime — 1 October 2026

## Scope and release state

Baseline: released commit `d8b701e40584d748855aa8cbec8aed1013ab46f2`. That release fixed client recovery and cancellation; this follow-up audits whether backend work actually observes disconnection and has finite embedding/request budgets. Changes remain local and uncommitted in the selective-release-check worktree. The primary checkout and prior testing-document follow-ups are preserved. No frontend source, UI styling, credential, production environment, migration, or live database record is changed.

## Reproduced root issues

1. **Backend cancellation did not follow client lifetime.** `chat.controller.ts` checked `res.destroyed` only after a generated chunk arrived. During catalog retrieval, embedding, model setup, or a stalled iterator, closing the response did not abort work. The signal was absent from the controller/service/RAG/provider contracts. Setup could subsequently write sources to a closed response. Existing provider fallback was not able to distinguish abandoned work from an ordinary provider failure.
2. **Embedding and aggregate request waits lacked deadlines.** `generateEmbedding` supplied no request options to Gemini. Per-model generation timeouts existed, but did not bound retrieval plus all attempts as one request. A stalled embedding or database wait could keep the controller pending indefinitely. The installed SDK's timeout implementation also schedules timeout timers without clearing them after success; the application now owns model deadlines and supplies a signal instead of relying on those retained SDK timeout timers.
3. **Model fallback could exceed the client's idle-gap budget.** The backend emits sources before generation and buffers each model attempt's answer before exposing text. Four default 15-second attempts can exceed the released client's 30-second byte-gap deadline. A stalled-generation regression reproduced zero keep-alive writes over 30 seconds, despite the request remaining within its total budget. The repair sends SSE comment heartbeats every 15 seconds while the request is active; these comments carry no answer or history and stop on completion/disconnection/deadline.

The initial controller/Gemini regression run had seven failed assertions and seven passes. These are not seven independent production incidents. The normal-request-close control additionally asserted the new signal contract; the baseline already ignored normal request-body close. One active-cancellation test initially used a polling interval longer than its 30 ms mocked model budget; it was corrected to 1 ms to observe active work rather than missing it. No production outage or quota-consuming provider request was induced.

## Focused repair

- `request-lifetime.ts` centralizes deadline ownership, signal-aware waits, and iterator cleanup. It rejects before starting pre-canceled work, removes abort listeners on resolution/rejection/cancellation, observes later asynchronous rejections, and requests iterator return without making a stalled cleanup block cancellation.
- Both JSON and streaming controllers create one request deadline spanning the complete Dr. Ai pipeline. They observe request `aborted` and response `close`, not normal request-body `close`, and dispose disconnect listeners/timers in finally. Closed/aborted clients receive no later writes. An active request that reaches its deadline gets the existing generic JSON 503 or terminal SSE error, never a successful done/history event.
- The same signal passes through chat service, RAG retrieval, embedding, and generation. Cancellation is rethrown before a retrieval-unavailable or source-only fallback can be treated as success. Ordinary provider failure still retains the grounded fallback behavior when the caller remains active. Existing prompts, evidence handling, pediatric safeguards, model order, attempts, and cooldown settings are preserved.
- Embeddings use one default **10-second** budget shared across all text chunks. A failed chunk cancels remaining chunk requests. Model attempts retain the existing default **15-second** budget, now owned and cleaned up by the application. The controller's default whole-request budget is **90 seconds** and is not restarted between stages or models.
- Environment parsing bounds embedding/model budgets to 1000–30000 ms and the whole-request budget to 1000–110000 ms. Defaults are documented in `.env.example` and `RAILWAY_VERCEL_DEPLOYMENT.md`; no production variable change is needed to use them after publication.
- Existing provider-error tests now use EventEmitter-backed request/response fixtures so they exercise the actual lifetime contract, while continuing to verify that provider details are not exposed to the client.
- Heartbeat ownership is restricted to streaming responses and cleared in finally. The actual released client parser ignores SSE comments as content and renews only its idle-gap timer; a new client compatibility regression proves heartbeats cannot extend its independent 120-second total deadline or manufacture an answer. Frontend source and styling remain unchanged.

## Limits and next release gate

An aborted HTTP request does not prove Gemini stopped remote computation or stopped billing. Signal-aware Prisma waits stop awaiting and prevent subsequent stages; they do not cancel an SQL query already submitted to PostgreSQL. Database statement budgets and hosting-proxy disconnect propagation remain separate infrastructure considerations. The existing frontend proxy is a deployment rewrite, not a new application streaming handler added by this batch.

No new live email/password cycle, administrator mutation, physical-device run, or participant acceptance result is claimed. No user browser tab was changed for these backend checks. No local fixture or fixture credential belongs in a production release.

Next gate: review the intended backend/config/test/documentation diff, obtain selective publication authorization, run the complete suite against isolated CI PostgreSQL, and only then release and inspect authenticated live completion/navigation behavior. The previously successful CI for `d8b701e` must not be counted as CI validation of this uncommitted backend batch.
